지원사업 추천을
명시적인 상태와 규칙으로

ESTC의 Entity · State · Transition · Constraint 개념을 기존 Next.js 추천 파이프라인에 가볍게 적용했습니다. 별도 에이전트 프레임워크나 세션 저장소는 도입하지 않습니다.

E · 개체

지원사업, 대화 메시지, 분류 결과, 후보 평가, 추천 카드.

기존 공통 타입과 원본 데이터를 재사용합니다.

S · 상태

요청별 검색 지역·출처·마감 설정, 처리 단계, 후보와 추천, 경고, 단계별 결과.

업력·업종은 미확인입니다. 검색 지역은 사업장 주소를 확정하지 않습니다.

T · 전이

입력 → 필터 → 분류 → 검색 → 평가 → 선정 → 완료.

순서를 벗어난 전이는 코드에서 거부합니다.

C · 제약

실제 대상 사업, 중복 방지, 출처·마감 필터, 유효 점수, 최대 3건.

조건 적합도와 검색 점수는 선정 확률이 아닙니다.

실제 처리 흐름

입력 검증→대상 필터→목적 분류→후보 검색→적합도 평가→추천 검증→설명 생성

Jev 분류·평가가 실패하거나 키가 없으면 해당 단계에서 로컬 처리를 사용합니다. 대화 모델 실패 시 기본 안내를 사용합니다. 빈 후보는 평가를 건너뛰되 선정·완료 단계까지 진행합니다.

처리 단계와 단계별 결과(success / local / skipped)를 구분합니다. 현재 기록은 요청 내부에만 존재하며 API 응답이나 영속 로그로 제공하지 않습니다.

시나리오 탐색

아래 예시는 실제 API 호출 없이 전이 규칙을 설명합니다.

분류와 평가 성공 → 실제 대상 사업에서 최대 3건 선정 → 수집 정보에 근거한 설명. Jev 적합도 0.3 미만은 추천에서 제외합니다.

장점과 비용

얻는 효과

  • 처리 단계와 로컬 대체 여부를 분리해 표현
  • 잘못된 전이와 카드 데이터 혼입을 코드로 방지
  • 출처·마감·점수 규칙을 최종 선정 시 재확인
  • 조건과 단계별 결과를 확장할 공통 위치 확보

비용과 한계

  • 상태 갱신 코드와 전이 테스트가 추가됨
  • 기존 검색의 후보 누락과 모델 품질은 그대로 남음
  • 최근 대화 범위 밖 조건은 유지하지 못함
  • 자유 형식 설명의 사실 검증은 별도 과제

이번 적용과 후속 확장

적용 완료: 요청 단위 상태, 단계 순서 검증, 단계별 결과 기록, 실제 데이터 기반 추천 선정. 기존 API 응답 계약과 외부 호출 수는 유지합니다.

후속 과제: 근거를 가진 기업 프로필, 업력·업종 추출과 정정 규칙, 장기 상태 유지, 상태 기반 추가 질문, 설명 본문 검증. 현재 검색 지역은 기존 최신 사용자 지역 해석을 사용하며 검색·모델 입력은 기존 대화 기반입니다.

ESTC는 설계를 명확하게 하는 수단입니다. 프롬프트 주입·환각 방지나 실제 지원자격 판정을 보장하지 않습니다. 불명확한 기간과 조건은 공고 원문 확인이 필요합니다.
